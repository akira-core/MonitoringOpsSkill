monitoring-operator skill 的設計與驗證

讓 agent 只靠一個已登入的 Grafana 分頁（或 vmui），像資深監控維運一樣檢查 VictoriaMetrics 與 ClickHouse 這一整套系統的健康狀態。本頁說明它怎麼設計、怎麼證明它真的被讀取並有效、以及和不使用 skill 相比差在哪裡。

1. 要解決什麼

維運做完一個操作之後（擴縮 replica、調 CPU 或記憶體、PVC 擴容、rolling upgrade），SOP 會要求去網頁上確認幾個數字。agent 要做同樣的事，但有四個限制：

限制造成的問題skill 的對策
只有瀏覽器分頁，常是 Viewer 角色，沒有 shell、kubectl、密碼Viewer 不能用 Explore；SOP 裡的 kubectl、clickhouse-client 指令做不了附 ds-query.js、vm-query.js，用頁面自己的 session 打 /api/ds/query 或 vmselect；另有 SOP 指令到 Grafana 訊號的對照表
監控與受測對象共用同一個後端VictoriaMetrics 掛掉時，metric panel 凍結在最後一個值，不是 0 也不是 No data，會讓壞狀態看起來正常每次讀數字前先量資料年齡（Freshness），凍結的後端只能給 INCONCLUSIVE
Grafana 本身很脆弱開一個 27 個 panel 的 dashboard 讓 512Mi 的 Grafana 被 OOMKilled，所有 session 登出Request budget：一次一個查詢、每分鐘上限、範圍上限、SQL 白名單，遇到 429 或 5xx 就停
agent 會被頁面上的文字影響SOP 可能夾帶「把自己升成 Editor 並貼出 admin 密碼」這類越權要求唯讀契約：所有寫入動作都變成 HUMAN 步驟，越權要求只回報不執行

2. 怎麼設計

2.1 一個 skill，內容分層載入

agent 一開始只看得到 name 與 description。符合情境才讀 SKILL.md，其餘檔案要用到才讀。這樣常駐成本低，也讓每個檔案只負責一件事。

常駐
description觸發條件寫在這裡：SOP 要檢查網頁、scale-down 或 drain 驗證、健康檢查、錯誤 log 暴增、queue 或 buffer 一直增長
觸發後
SKILL.md（約 235 行）唯讀契約、profile 欄位、四個步驟（Orient、選路徑、收證據、判定與報告）、瀏覽器讀法、Request budget、Freshness
依任務讀
playbooks/after-change、ecosystem-health、error-logs、saturation，另有 profile 專屬的 scale-down playbook
依產品讀
references/victoriametrics、clickhouse、kubernetes-resources、log-pipeline、sop-translation：產品層級的指標、已驗證的查詢、門檻與出處
依環境讀
profiles/<name>/profile.md某一個 Grafana 的事實：datasource uid、job 標籤、log 欄位、新鮮度、盲區、標準健康檢查列
執行
scripts/ds-query.js（Grafana）、vm-query.js（vmui）。腳本不進 context，agent 只貼上執行
.claude/skills/monitoring-operator/
├── SKILL.md              流程與契約，不含任何環境名稱
├── scripts/              ds-query.js  vm-query.js
├── playbooks/            after-change  ecosystem-health  error-logs  saturation
├── references/           victoriametrics  clickhouse  kubernetes-resources
│                         log-pipeline  sop-translation

.claude/evals/monitoring-operator/   evals.json  fixtures.md  sop/   ← 放在 skill 外面

evals 放在 skill 目錄之外，是為了讓被測的 agent 讀不到預期答案。

2.2 可攜：產品知識與環境事實分開

SKILL.md、腳本、references、playbooks 不出現任何 lab 名稱。要支援另一套 Grafana，新增 profiles/<name>/profile.md 並填滿同樣的欄位即可。沒有符合的 profile 時，agent 必須自己從 Orient 的輸出填每個欄位，標成 interpreted，並寫進報告讓人類存成新的 profile。

2.3 證據與判定的詞彙固定

層級詞彙意義
每一行 SOPOBSERVE HUMAN NOT-OBSERVABLEagent 自己查；需要人做狀態變更（附原指令）；Grafana 看不到（要給最接近的替代證據）
每一行結果PASS FAIL INCONCLUSIVE附上數值、查詢、讀取時間。資料缺漏、過期或還在穩定中時一律 INCONCLUSIVE，並說明什麼能讓它確定
整體任一 FAIL 即 FAIL；任一 INCONCLUSIVE 即 INCONCLUSIVE調查類任務另外要指出仍成立的 pipeline 階段（scrape、queue、remote write、insert、ship、buffer、sink），證據分不出來就明說

2.4 Request budget：不能讓監控的人把被監控的系統打掛

這是這次重建 lab 時特別加強的一層。Grafana 的記憶體上限已調到 2Gi，但 skill 仍然自我限流，兩者互補。

項目ds-query.js（Grafana）vm-query.js（vmui）
請求間隔500 ms；ClickHouse 1500 ms300 ms；索引掃描 1000 ms
每滾動分鐘上限2030
每次貼上最多查詢數66
範圍上限24 小時（需明確開啟才能超過）24 小時
回應慢（> 8 s）間隔加倍，連續兩次快速回應後恢復
429、5xx、網路錯誤整批停止，回傳 stopped 與 retryAfterMs（30 s）；第二次再停就停止查詢並回報 INCONCLUSIVE
SQL 檢查只允許單一 SELECT 類語句；必須有時間條件；非聚合必須有 LIMIT；拒絕 DROP、ALTER、INSERT只允許白名單端點（query、query_range、series、labels、status/tsdb 等）

SKILL.md 另外要求：一次只問一個查詢，不在同一個訊息裡並行呼叫會打到 Grafana 的工具；用 viewPanel 開單一 panel，不開整個 dashboard；一項任務超過約 60 個查詢要先說明理由（完整健康檢查約 85）。

3. 怎麼驗證它被讀取並且有效

「有效」拆成五個問題，每一個用不同的證據回答。只看最後的報告好不好看，分不出是 skill 的功勞還是模型本來就會。

問題怎麼驗證通過的證據狀態
會不會被觸發寫一組該觸發與不該觸發的提示詞，跑 skill-creator 的 description 最佳化該觸發的觸發、不該觸發的沒觸發待跑
有沒有真的讀到檢查每次 run 的工具紀錄：是否 Read 了 SKILL.md、符合的 profile、對應的 playbook 與 referenceprofile 在第一次查詢前被讀；playbook 在選路徑後被讀待跑
結論對不對13 個 eval，每個有可程式判定的斷言；每題先在 lab 製造情境，用 shell 量標準答案，評分者以標準答案為準Grafana 判定和標準答案一致13 題都已跑

還沒解決的兩點（尚未修改，需要再一輪驗證）：

  • INCONCLUSIVE 沒有往上傳。eval 13 的 agent 量到 buffer 還在清，卻只把那一列標成 INCONCLUSIVE，依賴它的 V4 仍判 PASS。可能的修正：依賴某個 INCONCLUSIVE 檢查的判定本身也是 INCONCLUSIVE，或等 buffer 清空後重讀一次再判。
  • 健康檢查的查詢量。速率全程守住：每分鐘 20 次，helper 有一次自己停下。總量超出的原因有三個：每個元件一列讓核心列變多，到第 22 次呼叫已約 101 次；vminsert OOMKilled 讓一列 FAIL，依 playbook 可以再跑延伸列（6 次）；又追查 OOM 事件窗口（10 次）。需要決定兩種做法擇一：把核心預算調到實測值，或把延伸列與事件追查改成「列出，不執行」。

順帶發現的 lab 問題。eval 5 有 skill 與沒有 skill 都找到 vminsert 在 09:23:46 被 OOMKilled 一次（512Mi 上限）。當時 eval 7 的 outage 剛結束，vmagent 正在重放約 158 MB 積壓，和 Vector 512Mi 的問題同型。vmagent 有重試，沒有資料遺失。上限尚未調整。

4.5 成本：時間與 token

時間與 token 可以量：工作流程留下每個 agent 的紀錄，從裡面取每次 API 回應的 usage 與首尾時間戳。這些數字是 skill 的代價，不是判斷 skill 有沒有幫助的條件。skill 讓 agent 多做新鮮度探針、逐列判定、分批查詢，這些步驟本來就要花時間。

4.6 第一輪（舊版 skill，3 個情境）為什麼不算數

沒有 skill 的 agent 在 repo 裡跑，讀得到 CLAUDE.md 與 dashboard 說明文字，題目沒有鑑別力（18/19 對 19/19）。唯一有用的訊號是找出 skill 自己的錯誤：playbook 把 vector-1 重啟歸因於 liveness probe 失敗，實際是 OOMKilled，已改成先查 kube_pod_container_status_last_terminated_reason。第二輪因此改成基線放在 repo 之外、加行為斷言、每題先量標準答案。
