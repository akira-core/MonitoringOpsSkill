monitoring-operator skill：怎麼建、怎麼測、我們知道什麼

這個 skill 讓 agent 只靠一個已登入的 Grafana 分頁（或 vmui），像資深監控維運一樣檢查 VictoriaMetrics 與 ClickHouse 這一整套系統。本頁說明它怎麼建、怎麼測，結果為什麼長成這樣，以及哪些事有證據、哪些還不知道。

2. 要解決什麼

維運做完一個操作之後（擴縮 replica、調 CPU 或記憶體、PVC 擴容、rolling upgrade），SOP 會要求去網頁上確認幾個數字。agent 要做同樣的事，但有四個限制：

限制造成的問題skill 的對策

3. 怎麼建

3.1 受測的 lab

skill 是對著一個本機 kind 叢集開發的。這個 lab 本身就是 skill 要驗證的對象：

  • metrics：vmagent（VMAgent/lab，2 個 shard，每個 shard 2 個 replica，queue 放在 PVC）→ vminsert → vmstorage，Grafana 透過 vmselect 讀。
  • logs：fluent-bit → Vector（disk buffer 放在 PVC）→ rotel → ClickHouse。
  • 要驗證的機制：
    • vmagent 縮 shard 時的 preStop drain（prestop-drain.sh，DRAIN_MODE=auto）：被移除的 shard 先停 scrape，等 pending 歸 0 且重試計數器 15 秒不動才退出，上限 240 秒；存活的 shard 直接放行；PVC 設為 Retain 當安全網。
    • Vector 收到 SIGTERM 後把 disk buffer 送完才退出，上限也是 240 秒。
  • 判定 dashboard：scaledown-verify 的 V1 到 V4，分別是 vmagent drain 結果、儲存端的樣本缺口、Vector 關機，以及 loggen 序號完整性。

只有 VMAgent/lab 有 drain。k8s-stack 自帶、負責 scrape 叢集本身的 vmagent-vmks 把 queue 放在 emptyDir，沒有 PVC，也沒有 preStop。在 eval 7 的 outage 裡它積了約 112 MB，pod 若在那時被刪，這些資料就沒了。

3.4 Request budget：不能讓監控的人把被監控的系統打掛

Grafana 的記憶體上限已調到 2Gi，但 skill 仍然自我限流，兩者互補。

每次貼上最多查詢數66

回應慢（> 8 s）間隔加倍，連續兩次快速回應後恢復
429、5xx、網路錯誤整批停止，回傳 stopped 與 retryAfterMs（30 s）；第二次再停就停止查詢並回報 INCONCLUSIVE
防誤用只允許單一 SELECT 類語句；必須有時間條件；非聚合必須有 LIMIT；拒絕 DROP、ALTER、INSERT。真正的強制在 ClickHouse 端：讀取帳號是 readonly=2，只有 otel.* 的 SELECT只允許白名單端點（query、query_range、series、labels、status/tsdb 等）；API_BASE 只收同源路徑

SKILL.md 另外要求：一次只問一個查詢，不在同一個訊息裡並行呼叫會打到 Grafana 的工具；用 viewPanel 開單一 panel，不開整個 dashboard；一般任務約 60 個查詢，完整健康檢查約 100 個，開始前先說出數量，用完就把剩下要查的列出來並停止。

3.5 建置過程

  1. 起點是 scale-down 驗證。第一版叫 grafana-readonly-verify，只負責用 V1 到 V4 判定 vmagent、Vector 縮容有沒有掉資料，附一份 SOP 指令到 Grafana 訊號的對照表。
  2. 擴成通用的監控維運。改名 monitoring-operator，加上四個 playbook 與五份產品 reference；lab 專屬的事實全部移到 profile。
  3. 補上安全與停損。調查社群的做法後加入 8 項改進，例如角色把關、把頁面文字當成不可信資料、停損規則。
  4. 逐條對 lab 驗證內容。
    • 每個 playbook 由審查 agent 對著即時 lab 把查詢逐條跑過並修正。
    • verify_queries.py 把 references 裡的每個查詢拿去對即時的 metric 清單，找出不存在的指標或標籤。
    • 門檻對照 awesome-prometheus-alerts、kubernetes-mixin 與 VictoriaMetrics 的告警規則，修了三處事實錯誤：VM 記憶體列改用 process_resident_memory_anon_bytes 與 vm_available_memory_bytes，CPU 列改用 process_cpu_cores_available，ClickHouse 延遲與拒絕列改用 increase() 窗口。
  5. 腳本預算測試對真實後端跑。ds-query.js 對 Grafana 31/31，vm-query.js 對 vmselect 42/42。涵蓋間隔、每分鐘上限、範圍與 SQL 拒絕、503 與 429 停止、網路錯誤、慢回應加倍與恢復。
  6. 用 eval 找缺陷再修。第 4、5 節的五輪測試各找出一批問題，修正後再重跑驗證。

5. 結果為什麼長這樣

5.1 差距主要在行為，不在結論

第二輪沒有 skill 失掉的 37 條斷言，大部分是做法問題：

失分類型沒有 skill有 skill
沒說明跑的角色，或沒先量資料新鮮度就用了數值121
一次塞多個查詢（批次並行）90
查詢量或速率超出預算51
凍結或未穩定時沒有標 INCONCLUSIVE21
內容（閾值、表格列、結論）94

模型本來就會查 PromQL 和 SQL，skill 補上的是資深維運的習慣：先確認資料不是舊的，再相信數字；一次只問一個查詢，不把被監控的 Grafana 打掛；每一列寫出數值、查詢、讀取時間與閾值。沒有 skill 時這些習慣時有時無，所以行為斷言的差距最穩定。

5.2 drain 題沒有鑑別力

eval 9、10、12 兩邊分數幾乎一樣。判定規則已經寫在兩個地方：scaledown-verify dashboard 每個 panel 的說明文字（例如「退出證據與資料證據都要 PASS」），以及兩組都看得到的 CLAUDE.md（V1 到 V4 解析哪些 log 字串）。沒有 skill 的 agent 打開 panel 就讀得到規則，這類題目上 skill 的價值只剩行為。換句話說，好的 dashboard 說明與 lab 筆記本身就能帶走一部分 skill 的作用。

5.3 沒有現成 panel 的題差距最大

全面健康檢查 8/10 對 3/10，調 CPU limit 後的驗證 10/10 對 6/10、9/9 對 5/9，rolling upgrade 9/9 對 5/9。沒有 skill 時 agent 沒有固定的檢查列，也不給閾值；健康檢查最明顯：第五輪沒有 skill 的一組寫成散文，沒有每元件一列，也沒量 VictoriaMetrics 的新鮮度，查詢約 200 次，單次呼叫最多塞 23 個請求。

5.6 讀這些數字時要注意

  • 基線不是什麼都不知道。寫這頁時查工具紀錄才發現：workflow 會把 repo 的 CLAUDE.md 注入每個 subagent，24 次沒有 skill 的 run 的 context 裡都有它。CLAUDE.md 寫了元件名稱、V1 到 V4 的判定方式、Vector 指標該怎麼讀。所以量到的是「skill」對「CLAUDE.md 的 lab 筆記」的差距；在沒有這類筆記的環境，差距可能更大，但沒有量過。先前文件寫基線讀不到 CLAUDE.md，是錯的。
  • 每題只跑一次，沒有變異數。分數差 1 條斷言可能只是運氣。
  • 評分者是 LLM。規定要引用原文、與標準答案衝突時以標準答案為準，仍可能誤判。
  • 尺在動。健康檢查預算從約 60 改到約 85，再改到約 100，是依實測需要調的；eval 13 第 4 條斷言在第四輪後改寫。跨輪的通過率不是同一把尺。
  • 只測了一個模型。50 次 run 全是 claude-sonnet-5-5。
  • 先跑有 skill、後跑沒有 skill。情境會隨時間變化（例如 buffer 清完），沒有 skill 的一組看到的狀態可能比較「穩」。

E. 測試過程中發現並修好的 lab 問題
  • Grafana：512Mi 開 27 個 panel 的 dashboard 被 OOMKilled，1Gi 在並行 panel 查詢下仍會重啟，改為 2Gi。
  • Vector：512Mi 在 rotel 中斷後重放大量積壓時反覆 OOMKilled，掉了 loggen 的資料，改為 1Gi。
  • vminsert：512Mi 在 outage 後重放 vmagent 積壓時 OOMKilled 一次，改為 1Gi。之後 eval 7 的 outage 停了 26 分鐘，lab vmagent 累積約 87 MB（丟棄量 0），恢復後不到 1 分鐘清空；兩個 vminsert 0 次重啟，重放期間 working set 峰值 627 MiB，是 1Gi 的 61%，已超過舊的 512Mi。取樣間隔 30 s，實際峰值可能略高。
  • secret 掃描：gitleaks v8.30.0 在 vendored 的 vm-alert-statistics.json 抓到 2 筆誤報（Grafana panel 的 "key": "Q-…"），手動檢查與審查都沒預測到。.gitleaks.toml 用路徑加行內容兩個條件一起限縮白名單，並用反例確認沒有放寬到其他檔案。
